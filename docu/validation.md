# v1 검증 기록

검증일: 2026-10-18. Windows, Python 3.12.10, 시스템에 설치된 Edge·Chrome의 헤드리스 모드에서 확인했다. 물리 스마트폰에서의 배경화면 적용은 이 검증에 포함하지 않는다.

## 지정 PS3 영상 기준 이동·형태 재구성

- 지정 영상의 물결 구간을 프레임별로 확인했다. 최초 181장에 누락 구간 6장을 보충하여, 유튜브가 제공한 약 29.97fps 스트림의 연속 번호 187장을 확보했다. 원본 파일을 내려받지 않고 브라우저에 표시된 프레임으로 분석했다. 분석 범위와 근사 맞춤의 한계는 [참고 자료](references.md)에 기록했다.
- 187장의 각 프레임에서 물결 중심을 추적했다. 총 4,397개 열의 표본을 사용했고, 로고가 보이는 초기 구간은 오른쪽을 제외했다. 7초 이후 위상 추적의 이동률은 약 0.0987 화면 너비/초로, 렌더링에서 확인한 약 0.1 화면 너비/초와 가깝다. 이는 큰 파형의 이동률 비교이며 모든 접힘의 형태가 픽셀 단위로 일치한다는 검사는 아니다.
- 고정된 기준점의 상하 진동을 공통 위상에 따른 오른쪽 이동으로 바꾸고, 넓은 면·앞쪽 접힘·위쪽 면·중간 접힘의 곡률과 음영을 조정했다. 파티클 궤도의 평균 높이는 새 물결 띠로 맞췄다.
- 실제 GPU 픽셀의 가로 빛 분포를 비교했다. 800×450, 12초 반복에서 0.5초 동안 40픽셀씩 오른쪽으로 이동했고, 네 시점에서 같은 방향·속도를 유지했다. 속도 2배에서는 79픽셀 이동을 확인했다. 물결이 화면 중앙 부근에 머무르는지도 검사했다. 결과는 `test-results/wave-motion-chrome.json`과 `test-results/wave-motion-msedge.json`에 생성된다.
- Edge·Chrome에서 새 이동 검사, 27가지 스타일·회전·화면비의 반복 경계, 기존 흰빛·입자·JPEG·MP4·취소·탭 닫기·오프라인 검사를 통과했다. API 테스트 28개와 Ruff 검사도 통과했다.
- PSP Classic과 PSP Original은 각각 0·2.5·5·7.5초의 869×482 이미지에서 변경 전후 RGB 차이 0을 확인했다.
- 12초는 참고 구간의 이동률에 맞춘 비교용 주기다. 기본 출력 길이 10초와 사용자가 지정한 길이는 유지하며, 짧은 길이에 한 주기를 넣는 속도 보정도 유지한다.
- 확인 영상 두 개를 실제 저장하고 끝까지 디코딩했다. 파란 기본색·입자 포함 영상과 참고색·물결만 있는 영상 모두 H.264, 960×540, 30fps, 12초·360프레임이었다. 결과는 `test-results/ps3-motion/ps3-motion-blue.mp4`와 `test-results/ps3-motion/ps3-motion-reference-color.mp4`, 시각 비교는 `test-results/ps3-motion/ps3-motion-reference-comparison.png`에 보관한다.

## 겹침의 흰빛과 얇은 경계 그라데이션

- PS3의 선택 프레임 8개를 비교했다. 자료의 해상도·탐색 시각·분석 범위는 [참고 자료](references.md)에 기록했다.
- 검은 배경·보라색 물결·입자 0개로 실제 GPU 픽셀을 읽었다. sRGB를 선형 색으로 되돌려 단순 밝기 증가와 색이 옅어지는 효과를 구분했다. 네 시점에서 밝은 부분의 채도가 면 내부보다 낮아지는지 검사했다.
- 시작 시점의 겹침 구간이 떨어진 면의 경계 구간보다 밝고 흰색에 가까운지 검사했다. 당시 곡면 모델의 Chrome 측정에서 두 구간의 밝기 지표는 약 170 대 104, 선형 채도는 약 0.41 대 0.73이었다. 이후 이동 모델 재구성에서는 검사 영역도 새 곡면 위치에 맞췄다. 이는 프로그램의 특정 검사 장면 수치이며 Sony 원본과의 수치 일치 검사가 아니다.
- Classic은 진한 파란 물결색을 지정해도 경계에 흰 반사광이 생기는지 확인했다. 869×482 출력의 하단 경계 한 지점에서 반치폭 8픽셀의 밝은 부분, 위쪽보다 아래쪽으로 긴 감쇠, `glow=0`에서의 반사광 제거를 검사했다.
- Edge·Chrome에서 새 음영 검사와 기존 반복·회전·화면비·입자·JPEG·MP4·취소·탭 닫기·오프라인 검사를 통과했다. 상세 수치는 `test-results/wave-lighting-chrome.json`과 `test-results/wave-lighting-msedge.json`에 생성된다.
- API 테스트 28개와 Ruff 검사 통과. PSP Original은 음영 변경 전후 네 시점의 RGB 차이 0을 재확인했다.
- PS3·Classic 확인 영상은 각각 960×540, H.264, 30fps, 10초·300프레임으로 실제 생성하고 끝까지 디코딩했다. 수정 전후 비교는 `test-results/wave-lighting-comparison.png`, 영상은 `test-results/ps3-lighting-preview.mp4`와 `test-results/psp-classic-lighting-preview.mp4`에 보관한다.

## 사용자 첨부 화면 기준 곡면 재구성

- PS3·PSP Classic을 사용자 첨부 화면과 비교하고 유튜브 영상을 브라우저에서 재생·탐색해 네 장면과 세 장면을 각각 확인했다. 영상의 녹화 환경과 재현 앱 여부는 [참고 자료](references.md)에 구분했다.
- Classic의 큰 상하 곡면, 파랑·청록 색 분포와 경계의 빛을 조정했다. PS3는 면별 독립적인 3차 곡선 구간과 주기적인 기준점 이동으로 교차·폭 변화를 표현했다.
- PSP Original은 변경 전후 0·2.5·5·7.5초의 869×482 렌더링을 비교해 RGB 차이 0을 확인했다.
- API 테스트 28개와 Ruff 검사 통과. Edge·Chrome에서 반복·회전·화면비, 입자 크기·초점, JPEG·세 스타일 MP4, 취소·탭 닫기·오프라인 검사를 다시 실행했다. 회색 팔레트에서 원치 않는 색이 생기지 않는지도 검사한다.
- 시각 검토용 PS3·Classic 960×540, 10초·30fps 영상을 실제 제작했다. 자동 검사만으로 원본과 시각적으로 동일하다고 판단하지 않는다.
- 확인용 결과물은 `test-results/`에 보관하며 Git에 포함하지 않는다.

## 기본값 2판과 입자 조절 추가 검증

- API 테스트는 28개 통과. 입자 크기 범위와 크기 필드가 없는 예전 요청의 호환성 검사 추가.
- Edge·Chrome에서 새 셰이더로 27가지 스타일·회전·화면비의 반복 경계와 JPEG·MP4 저장을 재검증.
- 검은 배경에 한 입자만 그려 크기를 키웠을 때 빛의 면적이 증가하고, 개수와 중심 위치는 유지되는 것을 실제 GPU 픽셀로 검사.
- 동일한 크기 설정에서 흐린 입자는 더 넓고 낮은 중심 밝기, 선명한 입자는 작은 면적과 높은 중심 밝기를 갖는지 검사.
- 입자 크기 설정을 바꾼 뒤 새로고침해 복원되는지 확인.
- 이전 저장 설정에서 기본값은 갱신되고, 직접 바꾼 색·회전·폭은 유지되는지 확인.
- 비교 화면: `test-results/revised-styles-final.png`. 초점 검사 수치: `test-results/particle-focus-chrome.json`, `test-results/particle-focus-msedge.json`.

## PS3 레이어별 움직임 검증 (2026-10-19)

- 네 면을 그리는 실제 GPU 함수의 양쪽 경계를 16비트 값으로 읽어, 공통 이동을 따라가는 좌표에서 상대 간격과 폭을 검사했다. JavaScript에 형상 수식을 따로 복사하지 않는다.
- 기본 높이에서 강도 0의 최대 상대 변화는 약 0.000031로 측정 정밀도 수준이었다. 강도 1은 약 0.066545, 강도 2는 약 0.151186로 증가했다. 같은 검사에서 네 면을 합친 최대 폭은 각각 약 0.176761·0.176272·0.176089로 비슷했다. 단위는 렌더러의 물결 좌표이며 완성 이미지와 참고 영상 사이의 오차 수치가 아니다.
- 높이 0·0.3·0.55·2에서도 변형이 높이에 비례하는지 확인했다. 높이 0에서는 새 굽힘이 생기지 않는다. 웨이브 속도 0에서는 강도 0·1·2 모두 정지했다.
- 강도 0·1·2 × 길이 1·10·12초 × 30·60fps의 18개 조합에서 시작·종료 RGBA가 일치했다. 반복 경계 양쪽의 짧은 시간 간격으로 GPU 경계 곡선의 변화 방향도 검사했다. 1초 영상은 한 프레임 사이에도 얇은 빛줄기가 여러 픽셀 이동하므로 이미지 밝기 변화와 곡선 속도 검사를 구분한다.
- Edge·Chrome 각각 45개 스타일·회전·화면비 조합을 통과했다. 기존의 거의 완벽한 평행이동 검사는 강도 0에 적용하고, 기본값은 레이어별 상대 변화 검사로 확인한다. 흰색 교차 음영 검사도 두 브라우저에서 통과했다.
- 이전 커밋의 셰이더와 직접 비교했다. PSP 두 스타일은 144개 조합, 파티클만 그린 화면은 12개 조합 모두 RGBA가 같았다. PS3 강도 0은 36개 중 33개가 같고, 나머지 3개도 각 화면의 한 채널에서만 8비트 값 차이 1이었다.
- 새 슬라이더의 표시·범위·0.05 간격, 1.65 저장·복원, 기본값 1 복원, 제작 중 잠금, PSP에서 숨김을 확인했다. 판번호 2의 저장 데이터에 새 필드가 없을 때 색·폭·회전·입자 크기를 유지하고 새 값만 1로 채웠다. 기존 판번호 마이그레이션도 통과했다.
- 실제 내보내기 경로로 파란색·입자 포함 영상과 참고 색상·입자 없는 영상을 제작했다. 둘 다 960×540, H.264, 30fps, 12초, 360프레임으로 전체 디코딩했다. 경계의 평균 RGB 차이는 약 0.524·0.538, 양옆 프레임 구간의 평균은 약 0.386·0.340이었다. 압축 차이가 포함되므로 무압축 GPU 반복 검사와 함께 판단한다.
- 수정 전후 12초 비교 영상과 0·3·6·9초 비교 화면, 고급 설정 화면을 `test-results/ps3-layers/`에 저장했다. 390px 화면에서 새 설정을 포함해 가로 넘침이 없는지 확인했다. 기하 움직임은 참고 영상의 특징을 본뜬 자체 근사이며 원본과 픽셀 단위로 같다는 의미는 아니다.

## 자동 검증

- API·인코더·설정 테스트 34개 통과: 설정 검증, 새 레이어 강도의 범위·유한성·생략 호환성, 28개 프리셋, 실제 H.264 출력, 30/60fps, 1×1·홀수 크기, 색 채널·상하 방향·가장자리 확장, 단일 작업, 취소, 탭 연결 종료, 잘못된 프레임 순서·헤더·크기, 디스크 오류 주입, 세션 종료 정리.
- Ruff 검사 통과. 테스트 클라이언트의 httpx 관련 상위 라이브러리 지원 종료 예정 경고 1건은 있으나 테스트 실패는 없다.
- Python 패키지 wheel 빌드와 오프라인 실행 자산 11개의 포함 여부 확인.
- `pip check`에서 의존성 충돌 없음.
- 실제 서버에서 인코더가 켜진 상태로 `Ctrl+C` 종료 후 FFmpeg 프로세스 0개와 세션 임시 폴더 삭제 확인.

## 실제 브라우저

Edge와 Chrome 각각에서 다음을 확인했다.

- 회전 0°·45°·90° × 가로·세로·정사각형을 각 스타일에서 검사했다. PSP는 스타일별 9개, PS3는 강도 0·1·2 각각 9개로 총 45개 조합의 GPU 렌더링.
- 모든 조합에서 `renderAt(0)`과 `renderAt(T)`의 RGBA 바이트 차이 0. 경계 양쪽의 한 프레임 간격 변화도 검사.
- 속도 0에서 정지하며, 작은 양수 속도가 정지로 보정되지 않음.
- JPEG 저장 크기와 공통 렌더러 원본 대비 압축 차이 확인.
- 세 스타일의 MP4를 실제 생성·다운로드·디코딩. 코덱·fps·프레임 수·길이·크기 검사.
- 설정 복원, 웨이브 회전과 출력 해상도의 독립성, 기기 선택, 취소 후 재시작, 탭 종료 시 서버 작업 정리.
- 외부 네트워크 요청을 차단한 상태에서 편집과 출력 성공. 외부 요청 발생 없음.
- 1440×1000 데스크톱과 390px 너비 화면을 캡처하여 레이아웃 확인. 가로 넘침 없음.

## 출력 크기 검증

| 출력 | 확인 결과 |
|---|---|
| JPEG 127×129 | 정확한 요청 크기 유지 |
| MP4 127×129 요청 | 가장자리 확장 후 128×130 |
| iPhone 16 1179×2556 요청 | MP4 1180×2556, 30fps, 1초, 30프레임 |
| 기본 세로 영상 | MP4 1080×1920, 30fps, 10초, 300프레임 |

표의 큰 해상도 검증은 파일 생성·인코딩 경로 확인용이다. PS3 음영을 다듬은 후에는 전체 스타일·회전·반복 검사와 작은 해상도의 저장·10분 제작 검사를 다시 실행했다.

## 장시간 제작

실제 Chrome 렌더러로 32×32, 600초, 30fps 영상을 제작하고 18,000프레임을 끝까지 디코딩했다. 출력 길이 600초 확인. 해당 PC에서 제작과 검사에 약 25초가 걸렸다. 이 시간은 큰 해상도의 제작 속도를 나타내지 않는다.

- Python 서버와 FFmpeg의 합산 작업 메모리: 약 60~84MiB. 하한에는 인코더 종료 시점이 포함된다.
- 브라우저 전체 프로세스의 합산 작업 메모리: 약 519~581MiB.
- 브라우저 JavaScript 사용 힙: 약 5.2~9.0MiB.

워밍업 이후 메모리가 전체 프레임을 누적하는 크기로 증가하지 않는 것을 확인했다. 측정 스크립트는 메모리 범위를 검사하며, 상세 로그는 `test-results/long-export-memory.json`에 생성된다. 브라우저 자동화·개발 도구의 메모리도 포함되므로 위 수치는 실행 환경마다 달라진다.

## 재현

실행·검증 명령은 [CLI 사용법](guide/cli_usage.md)을 따른다. 캡처·JPEG·MP4·메모리 기록은 `test-results/`에 생성되며 Git에 포함하지 않는다. 시각 재현의 근거와 제한은 [참고 자료](references.md)에 기록했다.
