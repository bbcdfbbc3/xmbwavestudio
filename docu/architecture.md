# 구현 구조

## 실행과 데이터 흐름

```text
Python 실행 → 127.0.0.1 서버 준비 → 기본 브라우저 열기
                                  ↓
                        Three.js / WebGL2 편집기
                         ├─ 작은 실시간 미리보기
                         ├─ 실제 크기 렌더링 → JPEG 다운로드
                         └─ 실제 크기 렌더링 → WebSocket → FFmpeg → MP4 다운로드
```

미리보기와 JPEG·MP4가 같은 `WaveRenderer.renderAt(config, time, size, duration)`를 사용한다. 시간 누적 시뮬레이션이나 해상도별 난수는 사용하지 않는다. 미리보기는 별도 화질 크기를 쓰지만 그래픽 좌표와 입자 시작값은 같다.

## 설정

- `SceneConfig`: 스타일·색·속도·회전·모양·입자·난수 시작값. 입자 크기 `particle_size`는 0.25~4, 기본 1이며 생략한 예전 API 요청에도 기본값을 적용한다. Python 모델에서 API 입력을 검증한다.
- `layer_motion`은 PS3 레이어의 상대 움직임 강도다. 유한한 0~2, 기본 1이며 이전 요청에서 생략해도 1을 적용한다. 다른 스타일은 이 값을 렌더링에 사용하지 않는다.
- `OutputConfig`: 출력 종류·크기·길이·fps. 길이에 임의의 최대 초 수를 두지 않고 프레임 수의 JavaScript 정수 계산 가능 범위를 확인한다.
- 스타일별 기본값과 28개 기기 해상도는 로컬 API로 제공한다.
- 브라우저 보관 키는 `xmb-wave-studio-v1`. 편집 설정만 저장하고 이미지나 영상은 보관하지 않는다.

## 그래픽과 반복

서로 다른 세 개의 분석적 그래픽 함수가 Classic의 화면을 넓게 덮는 반투명 면, Original의 아래를 채우는 넓은 두 곡면, PS3의 폭이 변하며 교차하는 실크층을 그린다. Classic은 위·아래 경계가 떨어진 큰 면과 경계 아래로 퍼지는 빛을 사용한다. PSP 두 스타일은 PS3 움직임 재구성에서 유지했다. GPU 계산은 선형 색을 사용하고 화면 출력은 sRGB로 변환한다.

PS3는 화면에 고정된 기준점을 위아래로 움직이던 방식을 없애고, 공통 이동 위상 `q=kx−phase`를 사용한다. 큰 물결, 넓은 뒤쪽 면, 좁아지며 교차하는 앞쪽 접힘, 희미한 위쪽 면, 중간 접힘이 이 흐름을 따라 오른쪽으로 움직인다. 넓은 면 안쪽에도 부드러운 중립 반사광을 주어 경계선만 떠 보이는 현상을 줄인다. 화면 중앙 부근의 높이와 폭은 사용자가 지정한 부팅 영상의 물결 구간을 기준으로 바꿨다. 입자 궤도의 평균 높이도 이 띠에 맞추되, 입자의 개수·크기·이동 주기는 유지했다.

각 면의 양쪽 경계와 반사 방향은 공통 함수 `ps3Layer`에서 구한다. 시간각 `θ`에 대해 레이어별 시간차는 `a(sin(θ+α)−sin α)+b(sin(2θ+β)−sin β)`다. 이 값을 `layer_motion`만큼 적용해 앞서고 늦어지는 정도가 시간에 따라 변하게 한다. 가장 큰 계수는 a=0.22, b=0.06이므로 강도 2에서도 시간각의 진행률은 최소 `1−2(0.22+2×0.06)=0.32`다. 공통 이동이 뒤집히지 않으며 네 면은 같은 띠에 머문다.

접힘 폭은 별도의 주기 함수로 최대 강도에서 ±18% 이내로 변한다. 굽힘 변화는 물결 높이에 비례한다. 모든 변화는 시작값을 빼서 초기 자세를 유지하며, 위치와 변화 속도가 반복 경계에서 이어진다. 속도 0에서는 시간각이 멈추므로 상대 움직임도 멈춘다. 강도 0은 기존의 고정된 상대 간격과 동일한 이동·음영 계산을 사용한다. PSP 렌더링과 파티클 셰이더는 변경하지 않는다.

기본 가로 화면에서 이동 위상은 화면 너비당 약 5.29라디안이다. 영상에서 추정한 큰 물결의 이동률 약 0.098 화면 너비/초에 맞춰 12초 주기를 비교 기준으로 사용한다. 이는 짧은 참고 구간의 근사 맞춤이며 Sony의 원본 애니메이션 주기를 직접 측정한 값은 아니다. 사용자 지정 길이는 바꾸지 않고 기존 반복 횟수 보정을 적용한다. 따라서 10초에 한 주기를 넣으면 같은 파형의 이동 속도는 12초 기준보다 약 20% 빨라진다.

색이 있는 면의 빛과 중립적인 흰 반사광은 따로 계산한다. PS3는 각 면의 픽셀별 빛 기여도 `eᵢ`에서 `(Σeᵢ)² − Σ(eᵢ²)`로 서로 다른 면의 겹침을 구한다. 혼자 있는 면의 자기 밝기는 이 값에 포함되지 않는다. 겹침이 강한 위치에 부드럽게 제한한 흰빛을 더해 색이 옅어지는 밝은 부분을 만든다. 흰빛은 움직이는 면의 기여도에서 매번 구하며 고정된 흰색 영역을 덧씌우지 않는다. 이는 참고 화면에 맞춘 음영 근사이며 Sony 엔진의 구현을 설명하는 수식은 아니다.

Classic은 경계 기울기를 반영한 거리를 사용해 흰빛 폭을 계산한다. 얇은 경계의 밝은 부분과 면 안쪽으로 짧게 감쇠하는 비대칭 그라데이션을 더한다. 상단과 하단의 빛 강도를 가로 위치에 따라 다르게 주어 둥글게 접힌 면의 노출 차이를 표현한다. 두 스타일 모두 흰빛에 기존 `glow` 값을 적용하며 새로운 설정 필드는 추가하지 않는다.

PS3 입자는 별도 인스턴스 사각형 드로우 호출로 합성한다. 하드웨어의 포인트 크기 제한에 의존하지 않아 큰 흐린 입자도 해상도에 비례해 확대할 수 있다. 고정 난수로 입자마다 깊이를 배정하고 선명한 빛점·십자 빛줄기와 넓고 흐린 원형 빛을 연속적으로 섞는다. 작은 선명한 입자는 픽셀 면적을 반영해 중심 빛이 사라지는 현상을 줄인다. 크기 슬라이더는 이 사각형만 확대하고 위치·개수·난수 시작값은 바꾸지 않는다.

입자는 물결 주변에 더 많이 분포하며 일부는 전체 배경에 흩어진다. 한쪽에서 반대쪽으로 이동한 뒤 투명한 구간에서 다시 시작하고, 수명이 시작·종료될 때 밝기 변화가 부드럽게 0에 도달한다. 반복 영상에서도 위치가 되돌아가는 순간이 보이지 않는다.

브라우저 저장 형식에 기본값 판번호 `revision: 2`를 기록한다. 이전 버전에서는 필드별로 옛 기본값과 같은 값만 새 스타일 기본값으로 바꾸고, 사용자가 바꾼 값은 유지한다.

`layer_motion` 추가 시 판번호는 올리지 않는다. 판번호 2의 저장값에서도 누락된 새 필드만 1로 채우고 다른 편집값은 유지한다. 고급 설정의 PS3 전용 슬라이더는 0~2, 간격 0.05이며 기존 저장·복원, 기본값 복원, 출력 중 편집 잠금에 함께 연결된다.

요청 속도 `s`, 영상 길이 `T`, 기본 주기 `P`에서 반복 횟수는 `s=0`이면 0, 그 외에는 `max(1, round(s×T/P))`다. 물결 `P=12초`, 입자 `P=16초`. 실제 표시 속도는 `횟수×P/T`다.

모든 시간 변화는 이 정수 반복 위상의 삼각함수와 정수 배수 조합으로 구성한다. 입자 궤적과 반짝임도 같은 방식이다. 시작과 종료에서 위치와 변화 방향이 함께 이어진다. GPU에 큰 절대 시간을 넘기지 않고 CPU에서 주기 내부 위상으로 줄여 전달한다.

출력 프레임 `i`의 시각은 항상 `i/fps`. 느린 PC나 느려진 탭에서도 파일에 필요한 프레임을 모두 생성한다. 마지막 중복 프레임이나 끝부분 크로스페이드는 사용하지 않는다.

## 영상 전송과 상태

1. 출력 해상도로 실제 GPU 렌더링·픽셀 읽기를 시도한다.
2. `POST /api/exports`에 `{scene, output}`을 보내 작업을 만든다. 서버당 진행 중인 작업은 하나다.
3. `/api/exports/{id}/frames` WebSocket에 연결한다. 서버의 `ready` 응답에 전송 청크 크기가 포함된다.
4. 각 프레임은 `{"type":"frame","index":i}` 텍스트 헤더 이후 RGBA 바이트를 1MiB 이하의 바이너리 청크로 보낸다.
5. 서버는 순서와 정확한 바이트 수를 확인하며 FFmpeg 표준 입력에 즉시 기록한다. 한 프레임의 `ack`를 받아야 다음 프레임을 시작한다.
6. 마지막 프레임 이후 `encoding`, MP4 마무리 이후 `completed`를 보낸다. 진행 응답에 프레임 수·진행률·시간이 포함된다.
7. 완료 파일은 `GET /api/exports/{id}/download`로 스트리밍 다운로드한다.

브라우저는 최대 한 프레임의 RGBA 배열과 작은 WebSocket 전송 버퍼만 유지한다. Python은 작은 청크와 FFmpeg 파이프를 처리한다. 원본 프레임 시퀀스를 디스크에 저장하지 않는다.

상태 조회는 `GET /api/exports/{id}`, 취소는 `DELETE /api/exports/{id}`. 상태는 `ready → rendering → encoding → completed`, 또는 `cancelled/error`다. 연결하지 않은 준비 작업은 45초 뒤 정리한다. 연결 종료·잘못된 프레임·저장 공간 부족·인코더 오류는 작업을 종료하고 부분 파일을 삭제한다. 최종 MP4 마무리 중 탭이 닫혀도 종료한다.

## 파일과 실행 수명

FFmpeg는 창을 띄우지 않는 자식 프로세스로 실행한다. RGB 채널 순서를 유지하고, WebGL의 아래부터 읽는 픽셀 순서를 상하 반전한 뒤 yuv420p로 변환한다. 홀수 크기는 가장자리 픽셀을 반복해 짝수 크기로 확장한다. MP4는 `faststart`, H.264 CRF 18 / medium / 무음, BT.709 행렬·색 원색과 sRGB 전달 특성을 기록한다.

임시 영상은 OS 임시 폴더의 서버 세션별 디렉터리에 저장한다. 완성 영상은 서버 종료까지 다시 다운로드할 수 있다. 정상 종료 시 자식 프로세스를 종료하고 세션 폴더를 삭제한다. 강제 프로세스 종료나 전원 차단에서는 OS 임시 폴더에 파일이 남을 수 있다.

서버는 루프백에만 바인딩하고 브라우저의 쓰기 요청과 WebSocket Origin을 확인한다. 외부 렌더링 서비스, 분석 SDK, CDN, 원격 글꼴은 사용하지 않는다.
